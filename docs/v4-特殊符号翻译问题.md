是的，但要区分两件事：**数学上的 `√` 没有什么特殊含义，它就是根号；真正特殊的是它在 PDF 内部的存储/绘制方式。**

从你两张截图能很明显看出问题点：

第一张解析/翻译到：

> Since \(g_m\)  √

然后断掉。

而完整原文其实是：

> Since \(g_m \propto \sqrt{I_d}\), the power is reduced to 1/4 ...

也就是说真正的数学表达式是：

$$
g_m \propto \sqrt{I_d}
$$

这里很可能正好触发了你当前 PDF Parser 的边界问题。

### 为什么 `√` 特别容易出问题？

PDF 并不像 HTML：

```html
gm ∝ √Id
```

也不一定像 Word 那样保存一个完整的“公式对象”。

PDF 本质更接近于：

> **在坐标 (x,y) 上，用某字体画字符。**

因此视觉上看到：

$$
g_m \propto \sqrt{I_d}
$$

PDF 内部可能实际是：

```text
TextSpan: "Since "
TextSpan: "g"
TextSpan: "m"       ← subscript
TextSpan: " ∝ "
TextSpan: "√"       ← 数学字体中的 glyph
TextSpan: "I"
TextSpan: "d"       ← subscript

──────────────      ← 根号上面的横线甚至可能是绘制的 vector line
```

所以你眼睛看到的是**一个公式**，PDF Parser 看到的可能是 **5~7 个文字对象 + 一条矢量线**。

这就是关键。

## 你这个案例尤其典型

完整句子应该是：

```text
For a given gain, if the bandwidth is halved
from 0.7× data rate to 0.35× data rate, then Rd
can be doubled and gm can be halved. Since

gm ∝ √Id,

the power is reduced to 1/4 of that of a
```

```text

          ↓

"√"

          ↓

TEXT
```

然后你现在的算法发现：

```text
√
│
└── 与公式/图形保护区域相交
```

于是：

```text

    ↓

    ↓

    ↓

```

最终就出现了你前面看到的：

> 由于 gm ∝ √

这和你刚才报出来的异常：

> **与保留原文区域相交，已保留原文……由于 gm ∝ √**

是高度吻合的。

## 更麻烦的是：根号不一定是 Unicode `√`

这是你代码里一定要注意的。

你以为 PDF 里是：

```text
U+221A √
```

实际有可能是：

```text
Font: Symbol
Glyph: radical

或者

Font: MT Extra
Glyph ID: xxx

或者

Font: CMSY10
Glyph xxx

甚至：

√ + vector line
```

也就是说：

**屏幕上看起来都是 `√`，底层 PDF 不一定存在字符 `"√"`。**

所以你如果代码是：

```python
if "√" in text:
    ...
```

远远不够。

# 更推荐的解决方法

这个例子反而证明我们刚才说的 **AST + Inline Formula** 是必要的。

不要把这一整块定义成：

```text
████████████████████████
正文
████████████████████████
          █████
          公式保护区
████████████████████████
正文
████████████████████████
```

而应该恢复成：

```text
Paragraph
│
├── Text
│   "For a given gain ... Since "
│
├── InlineMath
│
│      gm ∝ √Id
│
├── Text
│   ", the power is reduced to 1/4 of that
│    of a conventional receiver..."
│
└── ...
```

然后送给翻译模型的内容可以是：

```text
For a given gain, if the bandwidth is halved
from 0.7× data rate to 0.35× data rate,
then [[MATH_RD]] can be doubled and
[[MATH_GM]] can be halved.

Since [[MATH_RELATION_01]], the power is reduced
to 1/4 of that of a conventional receiver...
```

其中：

```text
MATH_RD          = Rd
MATH_GM          = gm
MATH_RELATION_01 = gm ∝ √Id
```

翻译得到：

> 对于给定增益，如果带宽从数据速率的 0.7 倍减半至 0.35 倍，则 \(R_d\) 可以加倍，而 \(g_m\) 可以减半。由于 \(g_m \propto \sqrt{I_d}\)，因此其功耗可降低至传统接收机的 1/4……

最后排版引擎再把真正的公式对象放回去。

## 你的 Parser 现在应该增加一个很重要的规则

不要简单判断：

```text
TEXT bbox ∩ FORMULA bbox != ∅

→ collision
→ 保留原文
```

应该变成：

```text
发现碰撞
    ↓
判断是不是 Inline Math
    ↓
 ┌──是────────────────┐
 ↓                    │
提取 Math Span         │
 ↓                    │
拆成                  │
Text + Math + Text     │
 ↓                    │
重新组成 Paragraph     │
                      │
 ┌──否────────────────┘
 ↓
再判断是不是独立公式
 ↓
Display Equation
```

尤其要识别这些特征：

```text
√
∑
∫
∏
∝
≈
≤ ≥
±
×
α β γ Δ
上下标
分数线
根号横线
数学字体 Glyph
```

一旦它们出现在**正常句子的基线附近**，优先判断：

> **Inline Formula**

而不是：

> Formula Protection Rectangle。

## 甚至可以利用上下文把这个公式自动修复出来

例如 Parser 得到：

```text
Since gm ∝ √
```

下一批对象：

```text
I
d
```

结合：

* x/y 坐标；
* baseline；
* 字体；
* subscript；
* glyph；
* 字符间距；

重建：

```text
g_m ∝ √I_d
```

然后规范化为内部 LaTeX：

```latex
g_m \propto \sqrt{I_d}
```

这一步非常值得做。

你的内部数据不要继续存：

```json
{
  "text": "gm ∝ √Id"
}
```

最好存：

```json
{
  "type": "inline_math",
  "raw_pdf_elements": [...],
  "plain_text": "gm ∝ √Id",
  "latex": "g_m \\propto \\sqrt{I_d}",
  "bbox": [...],
  "render_mode": "original_pdf"
}
```

这样后面无论是**翻译、知识库提取、公式搜索、重新生成 PDF**都会容易很多。

### 所以，这次问题基本把根因暴露出来了

**不是大模型不会翻译 `√`。**

而更可能是：

> **PDF 中数学公式是由特殊数学字体 Glyph、上下标字符和矢量图形共同构成；当前解析器把视觉上的一个完整行内公式拆成了多个 PDF 对象，公式保护算法又进一步切断了原本连续的自然语言句子。**

所以我不建议继续加：

```text
遇到 √ 特殊处理
```

因为下一篇论文马上又会遇到：

$$
\frac{g_mR_d}{1+sRC}
$$

然后分数线出问题；再下一篇遇到：

$$
\sum_{i=0}^{N-1}
$$

上下标又出问题。

应该一次性解决成：

> **Inline Math Reconstruction（行内公式重建） + Display Math Detection（独立公式识别） + Text/Math AST（文本公式混合语义树）**

这会是你当前 PDF 专业翻译项目里非常关键的一次架构升级。
